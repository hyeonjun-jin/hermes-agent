# 기술조사 실행 안정화와 예산 제안

기준: 3960af19. **신규 유료 예산은 미승인·비활성**이다.
실제 OpenAI/논문/특허/공시 API 호출은 0회다. 아래 요청 수는 실제 모델 품질 평가가 아니라
Hermes 실행 루프에 Stub 응답을 넣어 확인한 프로토콜 요청 수다. 기존 운영 원장과 한도는 변경하지 않는다.

## 모델 요청과 도구 호출을 세는 방법

| 상황 | 필요한 모델 요청 | 설명 |
|---|---|---|
| Research 검색 API·조건 선택 | 1 | 한 응답에서 여러 검색 API를 병렬 선택해도 모델 요청은 1회 |
| 검색 API 실행·검색 결과 수신 | 추가 0 | P1의 로컬 도구 실행이다. API별 Tool 비용은 따로 기록 |
| 검색 결과를 읽고 원문 Read 선택 | 1 | 새 모델 요청에 직전 tool 결과가 포함됨 |
| Read 실행·원문 수신 | 추가 0 | 원문을 모델이 이해하는 단계는 다음 요청 |
| Research 역할 최종 응답 | 1 | 원문을 받은 뒤 요약·누락을 보고 |
| 추가 검색/재검색 | 라운드당 +1 | 현재 결과를 보고 재검색하면 최종 응답이 뒤로 밀림. 결과 수신 자체를 중복 계산하지 않음 |
| Analysis | 정상 1 | 수집 원문과 Research 결과를 입력받아 비교. 현재 유효 도구가 없어 정상 경로에서 추가 tool round 없음 |
| Verification 원문 재조회 선택 | 1 | 제공된 주장·원문을 보고 read/financial API 선택 |
| Verification 최종 응답 | 1 | 재조회 결과·기간·숫자·미확인 사항을 보고 |
| Verification 추가 재조회 | 라운드당 +1 | 여러 문서를 같은 응답에서 read하면 하나의 라운드 |

검색으로만 문서 ID를 얻는 일반 조사에서 최소는 R3+A1+V2=**6회**다.
재무 API처럼 원문을 직접 반환하는 경로는 검색 없이 R2+A1+V2=**5회**로 끝날 수 있다.
기존의 4회 Stub 경로(R2+A1+V1)는 Verification 재조회가 없었으므로 완전한 실행으로 보지 않는다.

## Stub에서 실행한 전체 흐름

| 경로 | Research | Analysis | Verification | 합계 | 결과 |
|---|---:|---:|---:|---:|---|
| 재무 원문 직접 조회·재조회 | 2 | 1 | 2 | 5 | 기존 역할 2회 한도에서도 완료 |
| 검색 → 원문 → 역할 최종 응답 | 3 | 1 | 2 | 6 | Stub 전용 제안 한도에서 완료 |
| 빈 검색 후 재검색 1회 | 4 | 1 | 2 | 7 | 완료 |
| 재검색 1회 + Verification 재조회 추가 | 4 | 1 | 3 | 8 | 완료 |
| 재검색 2회 + Verification 재조회 추가 | 5 | 1 | 3 | 9 | 정상 확장 경로의 명시적 상한 사례, 완료 |
| 기존 Specialist 2회로 일반 검색 조사 | 2 | 0 | 0 | 2 | Research 최종 응답 전 세 번째 요청 차단 |
| 원문 근거 누락 | 2 | 1 | 1 | 4 | 미완료 |
| Stub 비용 상한 0 | 0 | 0 | 0 | 0 | 첫 전송 예약 전 차단 |

9회는 무한한 재검색에 대한 자연적 상한이 아니다. 재검색을 2회, 추가 검증을 1회로
제한한 운영 사례다. 실제 모델은 더 많은 요청을 원할 수 있으므로 아래 hard cap으로 중단해야 한다.
원본 tool_calls, 실제 P1 실행 trace, 역할별 원응답과 최종 보고서는 실행 예제 JSON에 보존한다.

## 기존 한도의 영향과 이번 수정

현재 유료 경로는 전체 기존 12회 / 각 specialist 2회 / main 2회 / 출력 512 token을 유지한다.
기존 usage.json의 잔여 8회 미만·failed·pending이면 시작을 막는다. 원장이 없으면 새로 만들지 않는다.
일반 검색 조사는 Research가 이미 검색·read 2회를 사용한 뒤 최종 응답을 생성하지 못한다.
Verification에 추가 재조회가 필요해도 같은 2회 제한에서 중단한다. 전체 잔여가 있어도 역할 한도를 우회하지 않는다.

이번 실제 수정:

- 사용자에게 완료된 역할/중단 역할, 역할별 예약·요청 시도 수, 검색·원문 확보 여부,
  남은 Research/Analysis/Verification 작업과 중단 이유를 표시한다.
- 전송이 예약되지 않은 정책/비용 차단을 사용 호출로 계산하지 않는다.
- Real 완료에는 Verification의 성공한 원문 read/financial 재조회가 필요하다.
  원문 없이 최종 문장만 반환한 경우 실행 완료라고 표시하지 않는다. Mock 완료 기준은 유지한다.
- 중단된 역할의 원응답은 감사 기록에 남기고, 최종 보고서에는 명확한 중단 안내를 쓴다.
  Hermes의 일반 429 안내에 포함된 모델 전환/재시도 제안을 예산 우회 안내로 노출하지 않는다.
- 기존 Backend의 Real startup과 연구 Agent가 같은 canonical 원장 잠금을 공유한다.
  두 실행기를 업데이트한 뒤에는 동시에 원장을 소유할 수 없다. 이미 실행 중인 구버전은
  이 잠금을 모르므로 먼저 중지해야 한다. Mock Backend에는 잠금을 적용하지 않는다.

이미 정상 동작하던 것:

- Hermes tool-call 파싱, 다중 검색/read 호출, P1 schema·접근·반출 정책 검증.
- PUBLIC 전용 payload 검사, 원본 인용 span 검사, 원본 tool_call 감사 기록.
- 전송 전 pending 예약·원장 영속화, 재시작 후 과거 사용량 보존, 실패 미환불,
  private Memory 차단, 사용자/프로젝트 격리. 이것을 이번에 새로 구현했다고 주장하지 않는다.

## 권장 신규 정책 — 사용자 승인 전 제안만

| 항목 | 제안 | 상태 |
|---|---|---|
| Research | 최대 5회: 검색 1 + 재검색 최대 2 + 원문 선택 1 + 최종 응답 1 | 유료 경로 미적용 |
| Analysis | 정상 1회, 예외 수정용 최대 2회 | 2회째 정상 필요성이 실제 모델에서 확인된 것은 아님 |
| Verification | 최대 3회: 재조회 1 + 필요시 추가 조회 1 + 최종 확인 1 | 유료 경로 미적용 |
| 작업별 모델 요청 | hard cap 10회, 정상 범위 6~9회 | 유료 경로 미적용 |
| 요청당 출력 | R 1024 / A 2048 / V 1024 token | 현재 512 유지, 미적용 |
| 요청 크기 | 최종 messages+tools 직렬화 64,000 byte 이하 | 기존 경계 유지 |
| 도구 실행 | 작업당 12회, 중복·실패도 별도 비용 | 기존 P1 경계 유지 |
| 비용 | 작업당 예약 추정 상한 USD 0.11 | 미승인·미적용 |
| 시간 | 제안 작업 전체 240초, 원격 timeout 20초, 역할 timeout 60초 | 작업 전체 timeout은 제안만; 현재 역할/요청 timeout 유지 |

실패·중단: 역할/작업/금액/토큰/시간 한도, 정책 거부, API 오류·불명 usage/pending,
원문 누락, Verification 재조회 미완료. 완료되지 않은 역할을 완료로 표시하지 않는다.
재시도도 새 모델 요청으로 예약하고 실패한 요청의 예산을 환불하지 않는다.

### 비용 계산의 가정

기존 코드의 provisional 요율(입력 USD 0.15/백만 token, 출력 USD 0.60/백만 token)을 사용했다.
최신 가격을 조회하거나 실제 청구액을 측정한 것이 아니다. 승인 시 모델/요율·세금/환율 조건을 다시 확인해야 한다.

`추정 USD = 입력 token × 0.15 / 1e6 + 출력 token × 0.60 / 1e6`

입력 평균 4,000 token/요청, 각 요청에서 제안한 역할별 최대 출력을 사용한다고 가정하면:

- 6회(R3/A1/V2): 입력 24,000 + 출력 7,168 → 약 **USD 0.0079**.
- 9회(R5/A1/V3): 입력 36,000 + 출력 10,240 → 약 **USD 0.0115**.
- hard cap 10회(R5/A2/V3): 입력 40,000 + 출력 12,288 → 약 **USD 0.0134**.

입력 크기를 매우 보수적으로 byte 수만큼의 token으로 예약하면,
10 × 64,000 × 0.15/1e6 + 12,288 × 0.60/1e6 = **USD 0.1033728**다.
이를 감싼 제안 상한이 USD 0.11이다. 실제 tokenizer/과금 계약이 확정된 보장은 아니다.
호출 전에 상한을 예약하고 누적 예약+다음 예약이 상한을 넘으면 전송하지 않는 방식이다.
Stub 응답의 usage=10/5는 테스트용 값이며 이 예상 비용의 실측 근거가 아니다.
현재 Stub과 기존 유료 경로는 출력 512를 유지하며 제안 출력 한도를 활성화하지 않았다.

## 기존 원장과 신규 승인 예산 관리 제안

기존 usage.json의 calls/failed, 기존 총 한도·역할 한도는 보존한다. 경로 이동·삭제·초기화로
남은 예산을 만드는 기능은 제공하지 않는다. 이번에도 운영 원장은 제공/발견되지 않아 잔여를 확정하지 못했다.

별도 승인이 있다면 approval_id·승인자·작업 목적/사용자·유효기간·모델·가격 snapshot·최대
작업 수·요청/역할/금액/출력 한도·기존 원장 digest를 묶은 신규 grant를 등록하는 방식을 제안한다.
새 grant는 명시적으로 승인된 추가 credit이며 기존 잔여를 복제한 것이 아니다. 승인 원장과
기존 원장의 합산 감사·단일 coordinator를 사용하고 UI의 임의 파일 경로를 승인으로 취급하지 않는다.
이 등록/활성화 기능은 이번에 구현하지 않았다.

신규 승인에서도 기존 원장 anchor의 서비스 lease를 함께 잡아 구 Backend와 동시 전송을 막고,
안정적인 task_id/approval_id로 역할 사용량·pending을 보존해야 한다. 재시작은 새 작업 ID로
역할 한도를 초기화하는 '이어서 실행'이 아니다. 현재 앱은 재시작 시 사용량만 보존하며 자동
checkpoint 재개는 미구현이다. pending은 서버/관리자 조정 전 재전송·환불하지 않는다.

## Stub 실행의 안전 경계와 재현

```bash
python -m tech_research_agent.stub_workflow
```

StubWorkflowAdapter는 WorkflowStub 객체만 받고 OpenAI 전송 메서드는 무조건 실패한다.
UI/server Real 설정에서 선택할 수 없다. 임시 usage.json은 **Stub 전용 테스트 fixture**이며
운영 경로를 대체하거나 유료 예산을 활성화하지 않는다. 임시 원장은 실행 후 제거된다.
Runtime RealAdapter의 budget factory는 여전히 기존 ReservedBudget를 반환한다.
제안 역할/10회/비용 상한을 적용하는 StubBudget는 이 네트워크 금지 경로에만 있다.

별도 사용자 승인이 필요한 항목은 R5/A2/V3·작업10회, 출력 확대, USD 0.11의 유료 grant,
신규 승인 원장/작업 재개·coordinator 도입이다. 현재 기본 Mock과 기존 유료 한도는 그대로다.

## 이번 검증 기록

- 기존 회귀 포함 통합 **292 통과 / 0 실패** (206.6초, 파일 재시도 0).
- 마지막 비용/호출 한도 중단 문구 변경 후 워크플로 검사 **11 통과 / 0 실패**.
- 필수 정적 검사 19개 통과, 마지막 Ruff/health 2개 재검사 통과.
- 기존 Backend/Agent 공유 잠금 충돌과 해제, 실제 Backend Real startup의 잠금 참여,
  원장 bytes 보존, 10회 hard cap, 비용 예약 차단, 미완료 판정을 검사했다.
- [실행 기록 JSON](examples/stub_workflow.json)에 7개 경로의 요청 순서, 원본 호출,
  실제 도구 실행, 역할 원응답과 최종 보고서를 기록했다. 모든 transport는 stub-only다.
- 실제 API 호출 0, 운영 원장 변경 0, 유료 한도/출력 token 변경 0, 유료 예산 활성화 0.
- 실제 GPT-4o mini의 추론·개인화·업무 품질, 실제 청구액·latency를 검증한 결과가 아니다.
